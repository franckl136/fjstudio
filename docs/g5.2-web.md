# Courses Web hors ligne — recette G5.2

La version mobile `d0d8f110c7ebb6b3a0a354dd97ba8574dc3ba86e` a conservé une coche effectuée hors ligne après fermeture complète de Chromium. Le profil preview passe **9 contrôles sur 9**. Le profil authentifié relié à PostgreSQL passe **11 contrôles sur 12**. Le contrôle en échec concerne le délai de synchronisation d’une première coche effectuée en ligne.

La dernière liste avant le test d’expiration contient Haricots témoins en quantité 5, Poire témoin en quantité 6 et Riz long témoin en quantité 4, tous décochés. Le test d’expiration ajoute Avoine test en quantité 7. Pour la réauthentification, le navigateur utilise les contrôles e-mail et code de l’écran de connexion, le SDK de l’application et la même identité synthétique. Le serveur de recette délivre le code sans envoyer de courrier.

La navigation froide a utilisé le document renvoyé par le service worker. Le cache HTTP de Chromium avait été vidé avant la fermeture et désactivé dans le nouveau processus. Le premier processus avait quitté, son PID avait changé, le serveur de fichiers était arrêté et `navigator.onLine` valait `false`. Les lectures métier réussies et les applications de commande sur le serveur sont restées à zéro pendant cette phase. Chromium a enregistré des tentatives réseau locales en échec pendant la coupure. Aucune requête vers l’extérieur ni exception JavaScript non interceptée n’a été observée dans la campagne authentifiée.

La coche, le texte barré et IndexedDB concordent après les gestes. L’attribut `aria-checked` est absent dans les deux positions, sur les deux profils. Un lecteur d’écran ne dispose donc pas de cet attribut pour annoncer le changement. Aucune recette avec technologie d’assistance ni appareil Android ou iOS physique n’a été effectuée ici. La branche mobile développée indépendamment après le gel est hors de cette mesure.

### Délai de la première synchronisation

La campagne finale authentifiée a observé 4 reçus après 15 secondes. Le navigateur affichait l’article coché et son journal contenait une commande `check` en attente avec zéro tentative. PostgreSQL le conservait décoché. Lors d’une autre exécution du même commit, les cinq commandes avaient abouti dans la fenêtre. La reconnexion a vidé le journal dans la campagne finale. L’origine de l’intermittence reste à confirmer. Deux observations distinctes contiennent l’état des lignes, du journal, et le SHA-256 du reçu brut dont elles sont extraites. ## Export, session et isolation

Le générateur de l’application régénère le service worker à la fin de l’export Expo `static`. Dans chacun des deux builds, le manifeste décrit 110 ressources publiques totalisant 15 824 459 octets. Il comprend les documents statiques des routes `/` et `/courses`, le script d’inscription, les bundles et les assets. L’installation vérifie la taille et le SHA-256 de chaque fichier. Un échec retire le cache incomplet. La version précédente reste utilisable jusqu’à l’activation réussie de la suivante. Une première visite en ligne et une installation complète sont nécessaires pour une origine et un profil de navigateur donnés.

Les copies HTML mises en cache proviennent de l’export. Le worker télécharge ces ressources sans credentials et refuse les réponses privées, les redirections et les contenus divergents. Il ne prend en charge que les chemins, méthodes et types de navigation prévus. Le journal métier est conservé dans IndexedDB. L’authentification synthétique exerce le stockage de session normal du SDK sur ce profil Chromium éphémère. Aucun jeton, e-mail ou code de connexion n’est enregistré dans les pièces publiées.

Le navigateur Chromium Linux, le code de l’export et les deux services HTTP en boucle locale tournent dans un conteneur Docker Desktop Linux sur le PC Windows, avec pour unique interface `lo`, sans port publié, sans répertoire hôte monté et avec la racine en lecture seule. Le cache de paquets est monté en lecture seule et le processus s’exécute avec l’UID 65534. Chromium et le code testé partagent cet utilisateur dans le conteneur. Le banc vérifie un projet de confiance avec des données synthétiques.

Pour le profil authentifié, le SDK appelle une façade HTTP de recette. Les lectures et écritures passent dans un second conteneur PostgreSQL jetable, initialisé avec **19 migrations du commit** et le harnais SQL du projet. Le transport est un canal de messages limité aux tables et au RPC attendus. Les appels métier utilisent le rôle PostgreSQL `authenticated` et l’identité de test, et les écritures passent par la vraie fonction `public.apply_course_command`. Un contrôle distinct lit le nombre de reçus du journal SQL. L’authentification et la couche HTTP sont locales et synthétiques. Le profil preview utilise uniquement la persistance sur l’appareil.

## Reproduire

Prérequis utilisés sur Windows  •  Node.js 24, Git sous un répertoire système protégé, Docker Desktop Linux avec son canal local, et une copie du dépôt mobile contenant le commit. Le Studio et le dépôt mobile peuvent se trouver dans des dossiers distincts. Les six scripts `scripts/g52-web*` et `scripts/g52-sql-lab.mjs` accompagnent ce guide. Le parcours ne requiert aucun checkout d’une autre version du Studio. Le lanceur lit uniquement les objets Git nécessaires et produit son archive dans un dossier temporaire. Le code mobile s’exécute dans le conteneur.

Si les images ne sont pas déjà disponibles dans le moteur Docker local, les références utilisées sont les suivantes.

```powershell
docker pull mcr.microsoft.com/playwright@sha256:6446946a1d9fd62d9ae501312a2d76a43ee688542b21622056a372959b65d63d
docker pull node@sha256:873f586f3794f52281bd039bf02c048a0be08fde619338f9941bad1eb6b34530
docker pull postgres@sha256:1eff563f6c868b9b433566e9f3cf6e5c79fbd3b95bf70ec7277d376cdbfc50d7
```

Depuis la racine du Studio, renseigner le chemin de la copie mobile et utiliser le même objet Git pour les deux profils.

```powershell
$mobileRepo = Read-Host 'Chemin de la copie mobile'
$mobileGit = git -C $mobileRepo rev-parse --path-format=absolute --git-common-dir
$revision = 'd0d8f110c7ebb6b3a0a354dd97ba8574dc3ba86e'
node scripts/g52-web.mjs $mobileGit $revision prepare-cache
node scripts/g52-web.mjs $mobileGit $revision preview
node scripts/g52-web.mjs $mobileGit $revision authenticated
```

Le lockfile utilisé a le SHA-256 `67284de4f7341f0b91a9c8dab709c73fd169bedb7e52dc74012d4fbd0b5ac4ff`. La préparation vérifie les 677 archives, gestionnaire pnpm inclus. Lors de la préparation locale, 676 archives ont été réutilisées et seul `expo-secure-store` 58.0.3 a été récupéré. Les tarballs manquants d’un lock autorisé sont téléchargés depuis le registre npm public dans un conteneur distinct. Ce conteneur reçoit les coordonnées publiques et les empreintes. Pendant l’export et les interactions, l’installation pnpm utilise le lock gelé, le miroir en boucle locale et les archives contrôlées.

Le lanceur crée une nouvelle campagne dans `backups/g52-web/<id>`. Le JSON contient les verdicts individuels, les mesures SQL et navigateur ainsi que le SHA-256 du PNG. Les trois empreintes d’outil portent sur les scripts locaux en UTF-8 avec fins de ligne LF. Le lanceur Node prévoit le code de sortie 0 pour un profil qui passe tous ses contrôles, 2 pour un contrôle en échec et 1 pour une erreur d’infrastructure. Les deux conteneurs de la qualification finale ont été supprimés après exécution.
