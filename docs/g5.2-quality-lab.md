# Reproduire la campagne G5.2

## Consulter les résultats

Depuis la racine du Studio candidat, avec Node 24 et les dépendances installées par `npm ci` :

```powershell
npm run quality:g52
npm run quality:g52 -- show web-authenticated-g52
npm run quality:g52 -- show revue-g52
npm run quality:g52 -- compare reveil-delayed reveil-converged
node scripts/g52-catalog.mjs
```

La première commande vérifie les empreintes SHA-256 avant de donner un verdict par profil. La dernière reconstruit le catalogue en mémoire et vérifie qu’il correspond au fichier livré. La comparaison `compare <avant> <après>` du Quality Lab requiert des passages de même profil, environnement, jeu de données et projet. G5.1 et G5.2 ont changé de banc et parfois de contrat. La table de correspondance documente ces écarts. [Comparaison historique](g5.2-comparaison.md)

## Rejouer sur une copie de test

Le mobile doit être disponible localement à `d0d8f110c7ebb6b3a0a354dd97ba8574dc3ba86e`. Cette révision gelée n’est pas la pointe de la branche GitHub. Utiliser une copie de recette propre avec ses dépendances épinglées, Git Bash sur Windows et Docker Desktop en conteneurs Linux. Les deux conteneurs du profil authentifié restent sans réseau externe ni port publié. Le service HTTP de test traite une session SDK synthétique et des appels PostgreSQL en rôle utilisateur. Il ne simule pas le fournisseur de production de bout en bout.

```powershell
$mobile = (Resolve-Path '..\folkandjoy-G52').Path
$revision = 'd0d8f110c7ebb6b3a0a354dd97ba8574dc3ba86e'
$gitDir = (git -C $mobile rev-parse --path-format=absolute --git-common-dir)
$out = New-Item -ItemType Directory -Path (Join-Path $env:TEMP ('fj-g52-' + [guid]::NewGuid()))
node scripts/g52-sql.mjs $mobile (Join-Path $out 'sql.json')
node scripts/g52-client-review.mjs --source $mobile --evidence (Join-Path $out 'client-review.json')
node scripts/g52-web.mjs $gitDir $revision prepare-cache
node scripts/g52-web.mjs $gitDir $revision preview
node scripts/g52-web.mjs $gitDir $revision authenticated
```

Le banc SQL et l’export Web extraient leurs fichiers depuis Git. Le banc de revue vérifie les blobs des fonctions évaluées. La préparation du cache Web est une opération de développement distincte des essais hors réseau. Utiliser des archives de paquets référencés par le lockfile et les images locales compatibles indiquées dans les reçus. Un échec de scénario Web laisse un reçu avec les étapes menées et produit un code de sortie non nul. Chaque passage Web écrit sous `backups/g52-web/` dans un nouveau dossier annoncé en fin de commande.

Pour les suites du projet, dans une **copie de test propre** au SHA gelé avec les dépendances déjà installées, lancer `node scripts/g52-codechecks.mjs mobile <copie-propre> <nouveau-recu.json>` depuis le Studio. La commande exécute le lint, le typage, Vitest et les tests du shell. Le mode `studio` fait le typage et les tests de la version Studio, avec une base Compose de recette déjà préparée et un fichier local de configuration propre à cette base.

## Preuves et conservation

Les fichiers sources du dossier sont conservés tels que mesurés. Le catalogue enregistre leur empreinte. Les captures ne montrent que des articles synthétiques. Pour qualifier une nouvelle révision, écrire ses observations dans un nouveau dossier. Conserver les reçus, le type d’appareil, le SHA source et l’ordre des étapes, puis définir le profil de comparaison avant d’interpréter son verdict. Une absence de matériel donne NOT QUALIFIED. Une panne critique démontrée reste un FAIL même quand les suites de compilation et d’intégration passent.
